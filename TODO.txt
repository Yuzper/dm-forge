Right-click / context menus (app-wide)

Use Electron's native Menu.popup() — already used for spellcheck in electron/main/window.ts:50.
Renderer does the hit-testing and sends a menu template over IPC; main builds the menu and
resolves with the id of whatever was picked. One generic 'menu:popup' channel, not one per feature.
(Gotcha: menu.popup's callback can fire before the item's own click handler — resolve on a setTimeout 0.)

Key the menus by ENTITY, not by screen. The same things appear in many places — an article is a
wiki card, a relations node, a graph node, an autolinked span in the editor, a POI link target; a map
is a session tab, a hub card, an article section. Per-screen menus mean writing "delete article" five
times and watching them drift. So:
  src/utils/contextMenus.ts   -> buildArticleMenu(article, ctx) etc, plus dispatch
  src/hooks/useContextMenu.ts -> returns an onContextMenu handler
Right-clicking an article then gives the same menu everywhere, which is the whole point.

Where it's worth it:
 Tier 1 (real wins, action is buried or impossible today)
  - Map canvas. Three targets: POI, shape, and empty canvas. Empty canvas is the valuable one —
    "create POI here / start polygon here / measure from here" has no other natural home.
  - Article surfaces, especially relations-web and graph nodes, which have no per-node affordance at all.
  - Soundboard sounds. Edit/delete are hover buttons, loop is an icon toggle; fold them plus
    "assign hotkey" into one menu instead of more chrome on a dense grid.
 Tier 2 (cheap once the registry exists, pure accelerator — all already have kebab menus)
  - Session cards, DM notes pages/groups, campaign cards, loot table rows, timeline events.
 Tier 3 (skip)
  - Toolbar buttons, filter chips, rich-text editor body (default menu should win there).

Things to settle first:
 1. Text fields have NO context menu right now. window.ts:51 early-returns unless there's a misspelled
    word, so right-click in an input gives nothing — no cut/copy/paste/select-all. Native-only territory
    (renderer can't paste from a menu without extra plumbing). Fix in the same pass: handle
    params.isEditable -> editing menu, params.selectionText -> Copy. Entity menus layer on top.
 2. Right-click is already taken on the map — useShapeDrawing.ts:345 deletes a vertex on
    right-click while editing. Keep the gesture, but also surface it as a "Remove point" menu item.
 3. Right-click should select first (standard OS behavior), or menus act on something other than
    what's highlighted.
 4. No affordance, so right-click can never be the ONLY path to an action. Keep every kebab menu.
    Exception: the "create here" items on empty map canvas, which are inherently positional.

Trade-off accepted: native menus are OS chrome — light-themed on Windows regardless of the parchment
palette, no icons, no color swatches. Taken anyway because consistency across ~10 surfaces beats
theming, and it kills the positioning/z-index problems inside the zoomed map canvas. If a specific menu
needs a swatch or preview row, that one menu falls back to the existing menu-item pattern.

Open questions:
 - Does the empty-canvas menu include the create actions (making it a primary creation path competing
   with MapToolbar), or stay view-only?
 - Depends on the tabs system above: "Open in new tab" is the most common right-click item in an app
   like this. If tabs are coming soon, shape the article menu around it now instead of retrofitting.
